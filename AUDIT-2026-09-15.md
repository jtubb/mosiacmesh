# PART 0 — Video synchronization

## 0.0 Correcting my own earlier draft

An earlier version of this file announced a "root cause found." **That claim was overconfident and I am withdrawing it.** After reading the full `wall-cross-screen-sync-state` record, the situation is:

- Most of what I "found" about the 250 ms observer **was already known** (it is recorded as "the ~200ms bimodal-ct source").
- My proposed decode-deficit rebuttal was **wrong** — the fleet's ~2–3.5 % deficit is measured, not hypothetical.
- Your own record contains the exact warning I nearly walked into twice: *"measure the magnitude of a suspected error source BEFORE building a fix for it."*

What follows is therefore **not** a fix proposal. It is a **discriminating measurement** for a question the record leaves genuinely open.

## 0.1 Where the problem actually stands

The clock layer is **finished**. Per your v1–v4 diagnostic ladder: GoTime tracks ground truth to ~4 ms (optimal), crystals are healthy and common-mode (−19 ppm, 9 ppm spread), and the real cross-screen clock disagreement is **~27 ms median / 38 ms p90** (fit-based, trimmed). AP tuning moved nothing. The synctool `clock-disagreement` number (~300–500 ms) is outlier-and-uplink-jitter-dominated and **unreliable**.

So the remaining visible desync is the **video layer: ~150–220 ms video-offset**, roughly **7× the clock floor**. That is where the headroom is, exactly as your 2026-08-03 reframe concluded.

Within the video layer the record establishes:
- Rate **actuator** works ~1:1 across 0.5→2.0 via CMTimebase (open-loop, 5-load aggregate). **Not** the problem.
- Spurious 30 s seeks **fixed** by Lever A (30 s → 59 s median interval).
- Loop-boundary stall **fixed** (explicit-loop restart, merged).
- Cold-load / verr=3 **still open** (re-`load()` is the wrong recovery; recreate-element untested).
- Steady-state `ferr` sits at **−77…−206 ms, all behind clock, 128 ms cross-screen spread.**

## 0.2 The open question: is that −125 ms droop, or bias?

**Two mechanisms predict the observed `ferr` almost identically, and the record does not distinguish them.**

**(a) Classic P-droop against a real decode deficit.** A P-only law needs a standing error to hold a correction: `ferr = deficit / GAIN`. With the measured ~2.5 % deficit and `RATE_GAIN = 0.0002` (`drift-steer.js:11`):
> 0.025 / 0.0002 = **125 ms**

**(b) Sensor staleness bias.** `v.currentTime` is a **250 ms zero-order-hold with no timestamp** — verified at source this pass:

| Step | Code |
|---|---|
| Observer at 250 ms, **main queue** | `tweak/mmvideo/MMTransplantEngine.m:160` — `addPeriodicTimeObserverForInterval:CMTimeMake(1, 4)` |
| Value cached, not timestamped | `MMTransplantEngine.m:164` — `eng->curTime = mm_secs(t);` |
| Published to a global | `MMTransplantEngine.m:172` — `g_curTime = eng->curTime;` |
| JS getter returns the cache | `MMTransplantEngine.m:287` (`mm_ctrlCT`) and `:235` (`mm_engine_current_time`) |

Consumed raw at `index.html:1084` (`errorMs = v.currentTime*1000 - pos.offsetMs`), sampled every 500 ms (`index.html:1158`). Mean staleness of a 250 ms ZOH is **125 ms**, and it reads as a persistent *negative* `errorMs` — "always behind," which is exactly the observed one-sided signature.

> **Both mechanisms independently predict ≈125 ms, one-signed, behind.** The measured −77…−206 ms is consistent with either, or with a mix.

This matters because **they need opposite fixes.** Droop is cured by an integral. Bias is *immune* to an integral — an integral drives the *measured* error to zero, which parks the *true* position at exactly the staleness. If the residual is mostly (b), any amount of PI/feedforward tuning will keep failing, which is a fair description of the last several arcs.

### Two things the record shows have *not* been tried

1. **PI has never been retried since Lever A.** The recorded reason PI failed was *"an integral can't converge when a spurious seek resets the loop every 30 s."* Lever A removed those seeks. **The precondition that broke PI is gone, and PI was deferred rather than re-tested.** Branch `fix/drift-steer-pi-integral` already exists.
2. **The observer interval was shelved for the wrong reason.** `feat/mmvideo-currenttime-observer` (66 ms / off-main) was built and validated, then marked *"UNNECESSARY — the bimodal does not reproduce at settled full load."* That judged it against **readback noise**. The **staleness bias is not noise** — it is present by construction at every load, and scales directly with the interval. It was never evaluated against the metric that matters.

## 0.3 The discriminating experiment (zero deploy, zero fleet risk, one screen)

The two hypotheses split cleanly on one measurement, and **`ratetest.html` + `js/ratetestflag.js` already give you an in-webclip probe harness** (it runs inside Web.app where mmvideo lives — `uiopen`/Safari is not representative).

**Probe:** sample `v.currentTime` at ~20 Hz alongside `GoTime.now()`. Then compute two numbers:

- **`ferr_loop`** — what the drift controller currently sees (the 500 ms-sampled raw value). Expect ≈ −125 ms.
- **`ferr_true`** — the same error computed **only at staircase step edges**, where staleness ≈ 0. (Equivalently: the running **max of `ct_i·1000 − t_i`**, which is attained by the freshest sample.)

**Read the result:**

| Outcome | Interpretation | Next move |
|---|---|---|
| `ferr_true ≈ 0`, `ferr_loop ≈ −125` | **Bias dominates.** The video is physically near-correct; the controller is chasing a phantom. | Fix the sensor (§0.4). Do **not** retry PI first. |
| `ferr_true ≈ ferr_loop ≈ −125` | **Droop dominates.** The video really is behind. | Retry PI now that Lever A cleared the seek resets. |
| In between | Both present, in measurable proportion. | Sensor first (it's the cheaper, un-tried one), then PI. |

**Confirmations this same run gives you for free:** that `currentTime` advances in discrete ~250 ms steps (kills or confirms the ZOH premise outright), and the per-screen staleness phase.

**Why this ordering:** it is a *measurement*, on *one screen*, using *existing tooling*, that costs nothing and forecloses a wrong build. That is precisely the discipline the recvTs arc and the cold-load-watchdog arc were missing — both were sound builds against unmeasured premises, and both cost a full cycle.

## 0.4 If bias is implicated — the fix, in risk order

1. **Pure-JS staleness correction (no dylib, no fleet deploy).** Replace the raw read at `index.html:1084` with the max-of-recent-`(ct_i − t_i)` estimator. Cuts residual from *up to 250 ms, per-screen, slowly wandering* to *≈ the polling interval*. Testable on one screen via reload.
2. **Timestamp + extrapolate in the tweak (definitive).** Store `mach_absolute_time()` in the observer block; have `mm_ctrlCT` return `g_curTime + clamp(now − g_curTimeHost) × rate`. Staleness → getter latency, for every consumer, and **robust to main-queue starvation in a way that merely raising the observer rate is not**. Plain C, `mach_absolute_time()` only — no new ObjC class, so it respects the §14 loader fragility that killed KVO. Guard on `e->playing`; clamp (~400 ms) so a starved observer can't run away.
3. **Deploying the existing 66 ms branch** is a weaker version of #2 — it shrinks the bias ~4× but leaves it load-sensitive. Useful mainly as a fast corroboration if the probe is ambiguous.

# PART 1 — Verified defects

## 1.1 Offline detection is dead code — **[VERIFIED]**
**`server.py:2134-2141` · High · Bug**

```python
current_time = time.time()                       # 2120
for client_key, client in settings.clients.items():
    if client.isOnline:
        client.lastSeen = current_time           # 2136 ← refreshes ALL online clients
for client_key, client in settings.clients.items():
    if (current_time - client.lastSeen) > 60 and client.isOnline:   # 2141 ← always 0.0
```

Every client the stale check could apply to had `lastSeen` set to `current_time` moments earlier, so the delta is **exactly 0.0**. The 60 s check can never fire; the silence path to `CLIENTS_WENT_OFFLINE` is unreachable. A client only goes offline on a clean TCP FIN.

**Why it matters:** an iPad that drops WiFi without a FIN — the documented PSM/doze case — stays `isOnline = True` indefinitely. This is very likely the mechanism behind *"discovery API `online` field lies"* (recorded in `coordinated-start-arm-cap`), and plausibly behind the stuck-GO incident that `ARM_HARD_GRACE_MS` was added to paper over.

## 1.2 Reconnect-storm broadcast amplification — **[VERIFIED]**
**`mosaicmesh/broadcast.py:36-59` · High · Performance**

`_deliver` falls back to `socketmanager.broadcast()` on a targeted-send miss — sending **one client's** message to **every** session. The docstring argues this is bounded to "the affected client," but its own field note defeats that: *"19 of 22 reconnected iPads missed PREPARE."* 19 clients in the gap ⇒ **19 full-fleet broadcasts**, so each session absorbs ~19 × 16 KB ≈ 304 KB against mmws's 128 KB rx buffer. That is the overflow → teardown → reconnect-loop path you already fixed once by shrinking the payload; this re-multiplies it by the number of simultaneous reconnects.

*Caveat: overflow depends on JS drain rate vs. burst arrival — treat as the risk case, not a certainty.*

## 1.3 Edit during an in-flight render is silently dropped — **[VERIFIED]**
**`render_queue.py:37-38` + `render.py:1097-1101, 943, 961` · High · Race**

1. Render of (P, G) in flight ⇒ `_pending[(P,G)] == "RENDERING"`.
2. `render.py:1097` — `is_playlist_ready` is False during RENDERING, so it does **not** skip.
3. `render.py:1099` **overwrites the entry to QUEUED with the NEW token.**
4. `render.py:1101` — `enqueue` sees the key still in `_pending` → **returns False, no job scheduled.**
5. The in-flight render finishes and `render.py:961` writes **READY with the OLD token.**

Net: the entry reads **READY** while `is_playlist_ready` returns **False** (token mismatch), so PLAY is gated off. **The UI says READY while playback is blocked** — worse than FAILED, because there is no operator signal. Clears only on another save or a calibrate.

## 1.4 Failed render is resurrected by its own stragglers — **[VERIFIED]**
**`render.py:831, 822-828, 973` · High · Bug**

`asyncio.gather(...)` defaults to `return_exceptions=False`: the first exception propagates **but siblings are not cancelled**. The caller sets `FAILED`; each straggler then calls `progress_cb` → `_set_render_state(..., RENDER_RENDERING, ...)`, flipping FAILED back to RENDERING with nothing left to finalize it. Orphaned encodes keep burning CPU and writing output after the failure.

## 1.5 ffmpeg has no timeout — **[VERIFIED]**
**`render.py:613-615` · Med-High · Resource-leak** — `await proc.communicate()` with no `wait_for`. A hung encode pins the entry in RENDERING and holds a concurrency slot for the process lifetime.

## 1.13 mmcache buffers the WHOLE segment in RAM — caps usable clip length — **[VERIFIED 2026-09-17]**
**`tweak/mmcache/Tweak.x:110` · High (correctness) / blocks a product capability** — the download uses
`NSURLConnection sendSynchronousRequest:returningResponse:error:`, which materializes the **entire
response body as one in-memory `NSData`** before writing it to disk. That is deliberate: reading
`expectedContentLength` off the response is how the truncation guard verifies completeness before
caching, which is what fixed the old verr=3 "cached a truncated .mp4" bug.

The cost is a hard ceiling on segment size. The iPad-1 has `hw.memsize = 258,981,888` (**247 MB
total RAM**, shared with SpringBoard/mediaserverd/lighttpd), Web.app idles at ~37-42 MB RSS, and
[[gameoflife-warmup-jetsam]] records that 51-63 MB RSS was already enough to close webclips out. Every
segment ever shipped has been 3.5-6 MB, so this has never been hit — but a 10-minute PullTest4 render
produced **150 MB per screen**, an allocation ~60% of all physical RAM. It would either fail to
allocate (mmcache acks failure → falls back to streaming 150 MB centrally → AP saturation, see
[[full-video-wifi-bound]]) or trip jetsam and kill the webclip. Nothing relaunches a dead webclip, so
that is a permanently dark screen.

Measured encode rate for sizing: **0.2516 MB/s** of clip at a 0.25 s keyframe grid, **0.128 MB/s** at
1 s. Keeping segments ≤ ~15-20 MB means ≤ ~2 min of clip at a 1 s grid.

**Fix (deferred, recorded 2026-09-17 at the user's direction):** stream to disk instead of buffering —
replace the synchronous call with an async `NSURLConnection` delegate that appends each
`connection:didReceiveData:` chunk to an `NSFileHandle`, and verify the accumulated byte count against
`expectedContentLength` in `connectionDidFinishLoading:` (keeping the guard, losing the buffer). Memory
then stays constant regardless of clip length and the 2-minute cap disappears. It is a second native
tweak to build/canary/deploy, so it was held back while the mmvideo C1 canary is soaking. Workaround in
the meantime: keep clips short enough to stay inside the envelope.

## 1.14 A video's item window silently falls back to 20s unless `/api/media` was called — **[VERIFIED ON-WALL 2026-09-17]**
**`mosaicmesh/render.py:1349` (`_probed_video_seconds`) → `:1373` (`_duration_ms`) · High (correctness)**
— an "Auto"-duration video item gets its window from `_probed_video_seconds`, which is a **read-only
lookup** into `server._video_duration_cache`. That cache is populated by exactly one thing:
`GET /api/media`. On a miss the helper returns `None` and `_duration_ms` falls back to
`DEFAULT_ITEM_DURATION_S * 1000` = **20 000 ms**, silently.

So a video that is added to disk and put on the wall *without anyone opening the admin media list*
plays inside a 20-second window regardless of its real length. Nothing warns: the RENDER path is
unaffected (ffmpeg probes the source directly and encodes the full clip), so the segment on disk is
correct and only the **playback scheduler** is wrong. The two disagree.

**Observed:** `bbb_2min.mp4` (120.000 s) created 21:50, assigned + played 22:01 with no `/api/media`
call in between. On-wall telemetry: `elapsed - offset = 20000` exactly on every screen — the wall
cycled a 120 s clip every 20 s. 12 screens wrapped at the phantom boundary while 4 kept playing to the
file's real end, reading as a ~60 s cross-screen desync that was not a sync fault at all. Diagnosis is
arithmetic on the CLIENTLOG: `offset = ct - err`, then `elapsed - offset` is the window the client is
actually using.

The read-only design is deliberate and correct in itself (the docstring: ffprobe is async/blocking and
`_duration_ms` runs on the wire-build path). The defect is the **silent** fallback to a wrong-by-6x
window with no log line and no distinction between "this is an image/animation, 20 s is right" and
"this is a 10-minute video I failed to measure."

**Fixes, cheapest first:** (a) warm the cache where ffprobe already runs — the render path probes the
source to encode it, so have it populate `_video_duration_cache` as a side effect, which covers every
renderable item by construction; (b) failing that, log a WARNING when a `.mp4/.mov/...` item takes the
default window, so it is visible instead of silent; (c) probe asynchronously on playlist save.
**Workaround used on-wall:** set an explicit `duration` on the item (note this changes `me.duration`,
which is hashed into `render_token`, so it forces a re-render).

## 1.15 The device cache is effectively COLD after every page reload — **[VERIFIED ON-WALL 2026-09-18]**
**`js/mmCacheBackendMmvideo.js:13,52` + `tweak/mmcache/Tweak.x:184-193` · High (performance/correctness)**
— two facts combine into a re-download storm:

1. `_present` (the token→bytes map behind `mmCache.has()`) is a **plain in-memory JS object that
   starts empty on every page load**. It is populated *only* by `window.__mmCacheDone`, the native
   callback for a fetch that completed **in this page session**. Nothing enumerates the on-disk cache
   at startup. So after any reload the client believes it has cached nothing, however full the
   directory is.
2. The native `fetch` op has **no existing-file fast path** — `handle_mmcache` parses the token and
   goes straight to `dispatch_async_f(..., mm_download)`, which re-downloads the entire segment over
   the network even when the complete file is already sitting at `MM_CACHE_DIR/<token>.mp4`.

Net effect: **every reload re-downloads every segment.** At 3.5-6 MB segments this was cheap and
invisible. At 19 MB it is ~440 MB across 23 screens, throttled 3-at-a-time (`PrecacheWindow`, n=3),
taking 12+ minutes — and during that window screens either stream centrally (which an iPad-1 cannot
sustain for a segment this size) or hang. That is the real engine behind the "latch" cascade seen on
2026-09-17/18, not a video-element bug: reload a screen whose cache is cold and it streams centrally,
stalls, and the poll watchdog escalates to `wd-dead` ("stay black"). Reproduced deliberately on
sign1screen17 (10:14 2026-09-18): RELOAD → `vid:canplay`/`vid:playing` → `rs=4` → ct froze at 116000 →
`wd-retry` → `wd-dead` → back to `rs=0 ct=0`, ~10 s end to end.

There is also a **server/client bookkeeping split**: `client.cachedSegments` (server-side, what
`propagationPercent` reports) survives a reload, while the client's `_present` does not. So the server
can report a screen at 100% while the screen itself believes its cache is empty and streams centrally.
Do not trust `propagationPercent` as evidence of what a screen is actually playing from.

**Fix (small, native, safe):** short-circuit `fetch` when the file already exists — stat
`MM_CACHE_DIR/<token>.mp4` and, if present and non-empty, call `dispatch_done(token, size)` immediately
instead of downloading. This is sound *because* the write path guarantees completeness: `mm_download`
rejects any transfer whose length != `expectedContentLength` **before** writing, and writes with
`writeToFile:atomically:` flag 1, so a partial file can never appear in the directory. Presence
therefore implies validity. That makes `_present` refill from disk at reload speed, makes reloads free,
and removes the window in which screens stream centrally.
Cheap companion: have the JS backend ask the native side to enumerate the directory once at startup,
so `_present` is seeded without even a per-token round trip.

# PART 3 — Themes

1. **Silent-success failure modes.** §1.3 reports READY while blocking playback; §1.1 reports online for a dead device; §1.4 reports RENDERING for a failed job. Each hides from the operator, and §1.1 has already cost you a debugging cycle via the lying `online` field. A state-consistency assertion pass would catch all three.
2. **Reconnect storms compound.** §1.1 + §1.2 interact at exactly the worst moment.
3. **Event-loop blocking** (§1.6, §1.12, OpenCV-on-loop) delays `SERVERTIME` — server hygiene and wall sync touch the same loop.
4. **The sync investigation's recurring pattern is sound builds against unmeasured premises** (PI, feedforward, recvTs, cold-load watchdog — each correct in isolation, each not the dominant term). §0.3 is deliberately a measurement, not a build.
